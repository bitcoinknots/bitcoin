Long coinbase maturity: one year, expiring with RDTS
----------------------------------------------------

The temporary softfork that Bitcoin Knots 29.4.2 deployed to hold generated bitcoins for longer is extended: instead of ending at block 979920, it expires together with RDTS. Bitcoins generated by block 973440 or any later block cannot be spent in any block whose parent has a median time past earlier than 2027 September 1st 00:00 UTC. From the first block past that, they are spendable at the original maturity of 100 blocks.

This is a softfork on top of 29.4.2. Up to block 979919 the rules are the same, so nothing changes until then. Block 979920 is the first that 29.4.2 could accept and this version reject (one spending bitcoins generated since block 973440), so miners and nodes need to upgrade before it, expected around the end of October at the current block rate (the date moves with the hashrate).

A 29.4.2 node that upgrades only after block 979920 rechecks the blocks it connected from that height on at its first start: it rewinds to block 979919 and reconnects everything above it. A node coming from 29.4.1 or from another implementation has no record of having checked the long maturity rule at all, so it rewinds to block 973439 instead, as it would when upgrading to 29.4.2. Either way the rewind needs the block and undo data of those blocks, so a pruned node that upgrades late may have to reindex. Upgrading before block 979920 avoids all of this.

Policy and the wallet now apply the same delay to every coin generated by block 973440 or later, measured in time rather than in blocks: the mempool does not relay a spend of such a coin until the median time past of the chain tip is at least one year (365 days) past that of the block that generated it, and the wallet counts the coin as immature until then. Coins generated before block 973440 need only the original maturity of 100 blocks; 29.4.2 policy held them for 6480 blocks, which they all reach by block 979919. For the covered coins this is never sooner than the consensus expiry, which the mempool also enforces directly, so a wallet holding them can no longer select one that consensus would still reject. The GUI shows how many days such a coin still has to wait; the number of blocks to maturity shown for it elsewhere is an estimate, updated with every block.

A spend held by the consensus rule is rejected as `bad-txns-premature-spend-of-coinbase-long` and one held by the policy delay as `premature-spend-of-coinbase-long`; the original 100-block rule keeps `bad-txns-premature-spend-of-coinbase`.

`getdeploymentinfo` reports the expiry as `expiry_time` for `long_coinbase_maturity`, the same field RDTS uses, and no longer reports `height_end` or `maturity` for it. The regtest option `-testcoinbasematuritylong` now takes `<start_height>:<enforce_height>:<expiry_time>`.
